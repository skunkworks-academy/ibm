# Part 4: statistics, optimization, monitoring & performance

**Recommended time:** 8 hours

Performance work is an evidence discipline. The objective is not to make every metric “low” or every query “use an index.” The objective is to identify the dominant cost, understand why Db2 chose the observed access path, and improve service outcomes without shifting the bottleneck elsewhere.

<CourseProgress compact />

## Unit 1 · Begin with workload and waits, not configuration guesses

A useful performance baseline describes both demand and response:

- transactions/requests per second;
- response-time percentiles, not only averages;
- active connections and concurrency;
- CPU utilization and run queue;
- storage latency/throughput;
- bufferpool activity;
- sort and temporary-space behavior;
- logging rate and archive throughput;
- lock waits/deadlocks/timeouts;
- top SQL by total time, CPU, rows read or execution count;
- recent changes in application, data distribution, configuration or infrastructure.

## Unit 2 · Optimizer statistics are a model of the data

The optimizer estimates the cost of candidate plans using metadata about table cardinality, indexes, data distribution and other factors. If the model is stale or does not capture relevant skew/correlation, a plan can be reasonable for the model and poor for the real data.

### RUNSTATS decision questions

Before collecting more statistics, ask:

1. Has the table or index changed materially since the last collection?
2. Did distribution/skew change, or only row count?
3. Which predicates and joins are sensitive to selectivity estimates?
4. Are distribution statistics justified for the workload?
5. Is a statistics profile used to standardize collection?
6. What is the cost of collecting the requested detail on this object?

Illustrative pattern:

```sql
RUNSTATS ON TABLE APP.ORDERS
  WITH DISTRIBUTION
  AND DETAILED INDEXES ALL;
```

Do not copy this pattern blindly. On large objects, statistics detail has collection cost. Use the options that answer the workload’s estimation problem.

### Statistics profiles

Statistics profiles can standardize how statistics are collected for an object so recurring maintenance uses consistent options. The current CLA96G public objective set explicitly includes configuring and managing statistics profiles.

A profile becomes part of your operating standard: document why it exists, when it should be refreshed and what workload it supports.

## Unit 3 · Index design is a workload trade-off

An index can reduce read cost while increasing:

- storage;
- INSERT/UPDATE/DELETE maintenance;
- LOAD and maintenance work;
- backup size;
- optimizer search choices;
- governance complexity.

### Evaluate an index candidate

For each candidate, record:

```text
Target SQL / workload:
Predicates and joins supported:
Expected selectivity:
Current access path:
Expected new access path:
Read benefit:
Write/LOAD cost:
Storage estimate:
Overlap with existing indexes:
Validation workload:
Rollback/drop criteria:
```

Avoid creating near-duplicate indexes. Compare key columns, include columns, ordering and usage across the workload.

## Unit 4 · Design Advisor: recommendation, not authorization

Db2 Design Advisor can analyze workload information and propose physical design improvements such as indexes. The current CLA96G scope calls out using Design Advisor to obtain and implement index recommendations.

The DBA still owns the decision:

1. Is the workload representative?
2. What benefit is estimated?
3. Does the recommendation duplicate or overlap existing indexes?
4. What is the write/storage/maintenance cost?
5. Can it be tested on production-like data?
6. What metrics establish success?
7. What is the rollback path?

## Unit 5 · EXPLAIN: understand the selected access plan

EXPLAIN captures the access plan Db2 selects for an explainable statement. The statement is analyzed without being executed when using the standard EXPLAIN form.

Use EXPLAIN to answer questions such as:

- table scan or index access?
- join order and join method?
- estimated cardinality at each stage?
- predicates applied early or late?
- sort operations?
- estimated cost and row flow?
- whether a candidate index changes the plan as expected?

Common tooling includes SQL EXPLAIN tables plus utilities such as `db2exfmt` and `db2expln`, depending on the question and environment.

<Db2Terminal suggestions={['db2exfmt -d SAMPLE -1 -o explain.txt', 'db2expln -d SAMPLE -q "select * from APP.ORDERS where CUSTOMER_ID = 42"', 'db2 "explain plan for select * from APP.ORDERS where CUSTOMER_ID = 42"']} />

### Estimated vs actual is a diagnostic signal

If EXPLAIN expects 100 rows and runtime monitoring consistently processes millions, investigate:

- stale/incomplete statistics;
- data skew;
- correlated predicates;
- parameter sensitivity;
- expressions/functions reducing sargability;
- implicit data-type conversion;
- missing or unsuitable indexes.

## Unit 6 · SQL design signals

Before changing infrastructure, inspect query mechanics:

- are predicates selective and sargable?
- are data types aligned across comparisons/joins?
- is the query requesting unnecessary columns or rows?
- are joins logically correct and supported by suitable indexes?
- are sorts or repeated scalar functions dominating cost?
- can result sets be reduced earlier?
- is the workload executing the same expensive query far more often than expected?

A small application/query change can outperform a large infrastructure change when the dominant cost is unnecessary work.

## Unit 7 · Monitoring with SQL table functions and administrative views

The current CLA96G objectives include using SQL-based table functions and administrative views to retrieve real-time and historical monitoring data.

Design your monitoring queries around questions, not “collect everything.” Examples:

- Which statements consume the most total time?
- Where is lock wait time concentrated?
- Which utilities are currently active?
- Which table spaces are approaching capacity?
- Which applications have the oldest units of work?
- Are log/archive rates approaching configured or storage limits?

### Operational dashboard principle

Every dashboard tile should have:

- an owner;
- a threshold or expected range;
- a response playbook;
- enough context to avoid false alarms;
- a retention window appropriate to the decision.

Monitoring without ownership becomes noise.

## Unit 8 · db2pd, diagnostics and support evidence

`db2pd` is useful for low-overhead runtime inspection across areas such as applications, locks, memory and database state. Diagnostic tools such as `db2diag` and support collections are valuable when escalation is required.

Order matters:

1. capture lightweight, time-critical state first;
2. preserve diagnostic timestamps and identifiers;
3. avoid interventions that erase the condition before evidence is captured;
4. collect deeper support bundles when the initial domain is known or vendor escalation requires it.

A support bundle without a timeline is less valuable than a smaller evidence set tied to the incident window.

## Unit 9 · Db2 Data Management Console

A graphical console can accelerate correlation and communication by showing workload, resource and SQL behavior over time. Use it to support — not replace — the ability to explain the underlying metrics and SQL evidence.

When a chart shows a spike, be able to answer:

- what metric is being calculated?
- what interval/aggregation is used?
- which database member/service class/workload is represented?
- what changed at the same time?
- can the signal be reproduced with SQL/admin views or command-line evidence?

## Unit 10 · Db2 AI Query Optimizer

IBM’s current Db2 12.1 learning material includes AI-assisted query optimization. Treat AI-derived recommendations as another **decision signal**, subject to the same production controls as human recommendations.

A governed evaluation loop is:

```text
representative workload
→ baseline plan and performance
→ AI/advisor recommendation
→ controlled test
→ compare response time, resource cost and plan behavior
→ accept, reject or refine
→ document outcome
```

Do not let the word “AI” bypass change governance.

IBM published current operational guidance indicating that AI Query Optimizer model training consumes measurable CPU/memory during discovery/training. That reinforces the need to schedule and observe AI-assisted optimization like any other workload-affecting maintenance activity.

## Unit 11 · Build a performance experiment, not a tuning session

Use this template for every meaningful tuning action:

```text
Problem statement:
User/service impact:
Baseline window:
Workload volume/concurrency:
Dominant wait/cost signal:
Target SQL/object:
Current plan:
Hypothesis:
Proposed change:
Expected metric change:
Guardrail metrics:
Test window:
Result:
Decision:
Rollback / follow-up:
```

The guardrails matter. A query that improves 5× while batch write throughput collapses may not be a net improvement.
