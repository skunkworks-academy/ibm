## Unit 1 · Data Movement and Loading Fundamentals

Choose the mechanism according to throughput, logging, constraint behavior, recoverability and table state. SQL `INSERT`, `MERGE` and `TRUNCATE` operate differently from EXPORT/IMPORT/LOAD, and high-volume ingestion adds restartability and monitoring requirements.

### IMPORT vs LOAD is an operational decision

IMPORT uses SQL-style processing and obeys normal SQL semantics. LOAD is optimized for high-volume ingestion and can create utility/table states that require follow-up. A successful scheduler exit is not proof that the target is application-ready.

```bash
db2 list utilities show detail
db2 "select application_handle, utility_detail from table(mon_get_utility(-2)) as t"
db2 load query table APP.BIG_STAGE
```

ADMIN_MOVE_TABLE supports online relocation/change patterns with phased processing; INGEST supports continuous high-throughput ingestion with restartability and throughput monitoring.

## Unit 2 · Backup and Recovery

Distinguish crash recovery, version recovery and roll-forward recovery. Recovery design couples transaction logging, archive destinations, backup cadence/options, restore mechanics and validation.

### RPO and RTO drive the technical design

- **RPO** constrains acceptable data loss.
- **RTO** constrains acceptable recovery time.
- backup success alone proves neither objective.

Configuration such as `LOGARCHMETH1`, `NEWLOGPATH`, `LOGFILSIZ` and backup options must be considered with log generation rate, archive throughput and storage capacity.

HADR improves availability by shipping/replaying logs to a standby; it does not replace backup/recovery because logical mistakes can replicate. Pacemaker can participate in automated failover designs where supported and correctly configured.

Advanced patterns include logical/schema-level backup and restore, redirected restore and split-mirror copies. Each has prerequisites and consistency implications.

## Unit 3 · Database Maintenance, Monitoring, and Problem Determination

Use RUNSTATS, REORG and REORGCHK for distinct maintenance purposes; monitor with `db2pd`, `dmctop`, SQL table functions and event monitors; analyze SQL with Design Advisor and EXPLAIN; and use diagnostic/support tools such as `db2diag`, `PD_GET_DIAG_HIST`, `db2support`, `db2fodc` and `db2trc` when deeper evidence is required.

### Maintenance is condition-driven

RUNSTATS refreshes optimizer statistics. REORG changes physical organization. REORGCHK evaluates indicators. Do not schedule “REORG everything” as a substitute for measurement.

### Problem-determination evidence order

1. business impact and timestamp;
2. current database/instance state;
3. waits and active work;
4. utility/table-space/log state;
5. top SQL and plan evidence where relevant;
6. diagnostic logs/support bundles after the causal domain is narrowed.
