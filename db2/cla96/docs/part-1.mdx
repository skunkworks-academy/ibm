# Part 1: Essentials for Relational DBAs

**Self-paced allocation:** 8 hours · **Official unit structure:** 6 units

Part 1 establishes the Db2 administrator's operating model. The emphasis is scope: identify whether a fact, fault or change belongs to the installation, instance, database, storage or object layer before choosing a command.

## Unit 1 · Introduction to Db2 v12.1

Build a precise picture of the product before administering it: supported platforms, Db2 editions, client/connectivity choices, installation validation, licensing, VRMF/service levels and on-premises/cloud deployment models.

A production change record should identify the exact installed level rather than only “Db2 12.1”. `db2level`, installation records and compatibility requirements establish the maintenance baseline.

## Unit 2 · Db2 Command Line and GUI Tools

Use CLP, batch input, CLPPlus, Data Management Console and related command-line utilities as complementary interfaces. For enterprise operations, command output should be reproducible and captured as evidence.

```bash
# Interactive CLP
db2

# Non-interactive SQL with shell-safe quoting
db2 "select tabname from syscat.tables where card > 1000"

# Scripted input
db2 -svtf create.tab
```

Be deliberate about shell metacharacters. A `>` outside quotes is output redirection to the operating system, not a SQL comparison sent to Db2.

<KnowledgeCheck

## Unit 3 · The Db2 Database Manager Instance

An instance is the database manager runtime that can manage one or more databases. Instance configuration, registry/environment variables, instance identity and lifecycle commands have a broader blast radius than database-object changes.

```text
Host
└── Db2 installation
    └── instance
        ├── database A
        └── database B
```

Before `db2stop`, determine active applications, availability roles, automation/restart behavior and whether the action would destroy useful diagnostic state.

## Unit 4 · Creating Databases and Data Placement

Database creation decisions include storage, page size, table spaces, containers, extents, storage groups and database configuration. Automatic storage simplifies many operations, but the DBA still owns capacity, latency, failure-domain and recovery design.

Treat configuration as policy with four properties: **scope, activation, interaction and evidence**. Capture current values before `UPDATE DB CFG`, verify the effective value, test the workload and retain rollback values.

<Db2Terminal suggestions={['db2 get db cfg for SAMPLE', 'db2 "list tablespaces show detail"', 'db2 "select tbsp_name from table(mon_get_tablespace(NULL,-2))"']} />

<KnowledgeCheck

## Unit 5 · Creating Database Objects

Create and govern schemas, tables, indexes, views, aliases and triggers; understand declared/created global temporary tables, partitioning, MQTs, temporal tables, column-organized tables/BLU, external tables, referential integrity and constraints.

Every object has an operational cost. An index can improve selective reads but adds storage and write/LOAD maintenance. A partitioning or MQT design should be justified by workload and lifecycle requirements, not added by default.

<KnowledgeCheck
  id="p1u5-check"

  options={[
    'Indexes only improve performance and have no workload cost',

    'Indexes replace RUNSTATS and EXPLAIN',
  ]}
  correctIndex={1}
  explanation="Db2 physical design is a workload trade-off, not a one-direction optimization."
/>

## Unit 6 · Recovery and Troubleshooting Fundamentals

Part 1 introduces recoverable vs non-recoverable databases, logging and backup files, BACKUP/RESTORE/ROLLFORWARD/RECOVER DATABASE, recovery history and diagnostic files, and evidence-oriented troubleshooting with tools such as `db2diag` and administrative SQL.

Use the stateful simulator to practise a restore that leaves the database rollforward pending, then complete the recovery chain.

<Db2Terminal suggestions={['scenario recovery', 'db2 restore db SAMPLE from /backup/db2', 'db2 rollforward db SAMPLE to end of logs and stop', 'db2diag -A']} />
