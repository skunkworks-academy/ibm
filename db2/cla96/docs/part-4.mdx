# Part 4: Performance and Tuning Optimization

**Self-paced allocation:** 7 hours · **Official unit structure:** 4 units

Performance tuning is an evidence loop: workload → statistics/estimates → access plan → runtime behavior → controlled change → validation.

## Unit 1 · Statistics and Query Optimization

The optimizer estimates candidate plans using table/index metadata, predicate selectivity and data distribution. Incorrect or incomplete estimates can lead to an access path that is rational for the model but poor for the real workload.

Understand predicate classification, filter factors, frequency/quantile statistics, column-group correlation, statistics profiles, optimization classes, automatic statistics collection and Db2 AI Query Optimizer concepts.

```sql
RUNSTATS ON TABLE APP.ORDERS
  WITH DISTRIBUTION
  AND DETAILED INDEXES ALL;
```

Use statistics profiles to standardize justified collection options. Treat AI-assisted estimates/recommendations as additional evidence that still requires representative workload validation and change control.

## Unit 2 · Indexing for Performance Improvement

Select index types and key order from query patterns and workload costs. Evaluate range-delimiting/index-sargable access, include columns/index-only access, clustering, reverse scans and multi-index strategies such as Index ORing and Bitmap Index ANDing.

Monitor index usage with tools such as `MON_GET_INDEX` and `db2pd`. Use Design Advisor as a recommendation engine, not automatic authorization.

## Unit 3 · Using Explain Tools for Query Optimization

Create and maintain EXPLAIN tables; capture and interpret plans with `db2exfmt`, `db2expln` and activity/event data; generate reports and compare static/dynamic SQL diagnostics.

Use EXPLAIN to answer: access method, join order/method, estimated cardinality, predicate placement, sort operations and estimated cost. Then compare estimates with runtime evidence.

<Db2Terminal suggestions={['db2 "explain plan for select * from APP.ORDERS where STATUS = \'OPEN\'"', 'db2exfmt -d SAMPLE -1 -o explain.txt', 'db2expln -d SAMPLE -q "select * from APP.ORDERS where CUSTOMER_ID = 42"']} />

## Unit 4 · Monitoring Fundamentals

Understand Db2 monitoring architecture and use SQL table functions/administrative views, `db2pd`, `dmctop` and Data Management Console to observe current and historical behavior.

A useful performance baseline includes workload rate, response-time percentiles, CPU, storage latency, bufferpool behavior, sort/temp use, logging, lock waits, top SQL and recent changes. Metrics are useful when they answer an operational question and have an owner/playbook.

### Ten-minute triage

1. establish impact and time window;
2. compare demand with baseline;
3. identify dominant wait/resource domain;
4. identify top SQL/utilities/connections;
5. form one causal hypothesis;
6. collect the minimum evidence required to test it.
