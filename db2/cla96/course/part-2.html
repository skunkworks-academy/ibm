Part 2: recovery, utilities, maintenance & availability

Recommended time: 8 hours

Recovery is a service capability, not a backup command. A DBA should be able to connect business recovery objectives to log configuration, backup design, restore mechanics, validation and high-availability architecture.

Unit 1 · Start with RPO and RTO​

Two service objectives frame the technical design:

  • Recovery Point Objective (RPO): how much committed data the service can tolerate losing.
  • Recovery Time Objective (RTO): how long the service can tolerate being unavailable or degraded before recovery is complete.

A nightly offline backup may be technically successful and still be unacceptable if the business RPO is 15 minutes.

Translate objectives into controls​

RPO controls

Archive logging, backup frequency, log retention, replication/standby strategy and application consistency.

RTO controls

Backup/restore throughput, image accessibility, runbook quality, automation, standby readiness and validation time.

Proof

Timed restore/recovery exercises using representative data volume and application validation — not only a successful BACKUP return code.

Unit 2 · Backup strategy and evidence​

A backup plan should define:

  • backup type and cadence;
  • online/offline behavior;
  • image location and protection;
  • retention and lifecycle policy;
  • archive-log dependencies;
  • encryption requirements;
  • restore target(s);
  • validation procedure;
  • ownership and alerting.

Illustrative command patterns:

# Exact options vary by environment; validate against Db2 12.1 documentation.
db2 backup db SAMPLE online to /backup/db2 include logs

db2 list history backup all for SAMPLE

Capture the timestamp, image location, database alias, backup type and associated log requirements in your evidence note.

Security and backup media

Backup images can contain the entire logical dataset. Apply the same or stronger access, encryption, retention and disposal controls as the source database.

Unit 3 · Restore and rollforward as a recovery chain​

Think of recovery as a chain:

01 · Select imageConfirm source database, timestamp, image integrity and intended target.
02 · RestoreRestore the image to the correct database/storage layout.
03 · Apply logsRoll forward through the required log chain to the chosen recovery point.
04 · End recoveryComplete rollforward at end-of-logs or a governed point in time.
05 · ValidateCheck database state, application objects, consistency and business acceptance criteria.

A restore may complete successfully while the database remains rollforward pending. That is not an instruction to restart randomly; it is a state indicating recovery is incomplete.

Unit 4 · Point-in-time recovery and log-chain thinking​

Point-in-time recovery is a governed choice to stop before end-of-logs. The DBA must know:

  • the requested business recovery timestamp;
  • timezone and clock assumptions;
  • which backup image provides the recovery base;
  • whether all required archived/active logs are available;
  • the consequence for transactions after the chosen point;
  • how applications and downstream systems will reconcile the recovered state.

A technically correct database can still be operationally inconsistent with message queues, files, caches or external systems. Treat point-in-time recovery as an application-service decision, not only a database command.

Unit 5 · Redirected restore and storage re-mapping​

Redirected restore is useful when the target storage layout differs from the source — for example, a disaster-recovery host, migration, or lab recovery validation.

The reasoning sequence is:

  1. establish the source image and target database;
  2. inspect the source table-space/container layout;
  3. define target storage paths with sufficient capacity and correct ownership;
  4. perform the redirected restore steps for your Db2 level;
  5. apply logs as required;
  6. validate object state and application access;
  7. document differences from the source topology.
Use current syntax

Redirected restore syntax and supported storage patterns are configuration-sensitive. Use this course for the workflow model and IBM Db2 12.1 documentation for the exact command sequence in your environment.

Unit 6 · Advanced recovery patterns​

The current public CLA96G objectives call out advanced scenarios such as schema-level logical backup/restore, redirected restore and split-mirror copies. Treat these as design patterns with prerequisites, not generic replacements for database backups.

Logical/schema-scoped movement​

A logical export/restore approach can be appropriate when the recovery requirement is object/schema scoped rather than full physical database recovery. Evaluate referential dependencies, routines, privileges, sequences, data volume and application consistency.

Split-mirror or storage-assisted copies​

Storage-assisted copies can reduce backup windows and accelerate recovery, but only when Db2 and storage coordination guarantees a recoverable image. DBA and storage teams must share a runbook for quiesce/suspend/resume or the supported integration pattern.

Unit 7 · HADR fundamentals​

High Availability Disaster Recovery (HADR) maintains a primary/standby relationship using log shipping/replay. The DBA should understand at least:

  • primary vs standby roles;
  • synchronization mode and latency implications;
  • log shipping and replay health;
  • peer state and disconnect behavior;
  • takeover procedures;
  • client reroute/application reconnect expectations;
  • monitoring and alert thresholds;
  • the difference between high availability and backup/recovery.

A standby does not replace backups. Replication can faithfully reproduce an application error, unwanted delete or logical corruption.

Unit 8 · Utility monitoring and table states​

Data movement and maintenance operations can have states that affect application availability. Your runbook should never end at “command submitted.”

A utility evidence bundle should include:

  • operation type and start time;
  • object/database target;

Unit 9 · RUNSTATS, REORG and maintenance windows​

Maintenance must be connected to a condition:

  • large data change may justify statistics refresh;
  • poor clustering or physical organization may justify REORG;
  • object growth may change utility duration and log/temporary-space demand;
  • an online option may reduce outage but increase runtime/overhead.

Avoid “weekly REORG everything” as a substitute for evidence.

Part 2 review questions​
