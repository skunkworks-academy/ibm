Part 2 theory: every utility changes or proves database state

Part 2 joins three topics that are often taught separately: data movement, recovery, and maintenance/monitoring. Operationally they are connected. Utilities change data and object state; recovery reconstructs database state; monitoring and diagnostics tell you whether the state is usable and healthy.

Data movementThroughput ↔ logging ↔ object state

IMPORT, LOAD, INGEST and SQL movement make different trade-offs.

RecoveryBase image + ordered change

Backups and logs cooperate to reconstruct the required point in time.

OperationsObserve → maintain → prove

RUNSTATS, REORG, monitoring and diagnostics should be driven by evidence.

1. Data movement methods trade simplicity, throughput and control​

SQL INSERT/MERGE/TRUNCATE, IMPORT, LOAD and INGEST do not represent the same execution model. The DBA chooses among them by considering:

  • volume and throughput target;
  • logging/recoverability requirements;
  • constraints and triggers;
  • availability during the operation;
  • restartability;
  • object/table states after completion;
  • monitoring and validation needs.

The key principle is utility completion is not the same as operational completion. A LOAD can return control while the target still requires integrity processing or state validation.

2. Online movement minimizes outage by adding phases​

ADMIN_MOVE_TABLE illustrates a wider pattern: minimizing application outage often requires multi-phase work, staging/copy/replay behavior and a shorter controlled swap period. Online does not mean zero operational cost; it changes when and where the cost occurs.

3. Recovery is controlled reconstruction of state​

A backup is an important recovery input, but it is not the recovery capability itself. Recovery combines:

  • a known base state;
  • active/archived transaction history;
  • storage and configuration;
  • restore/rollforward procedure;
  • a governed target recovery point;
  • application/business validation.

RPO describes acceptable data loss. RTO describes acceptable service-restoration time. Backup cadence, archive logging, restore throughput, runbook quality and HADR design contribute differently to those objectives.

4. High availability and historical recovery solve different failures​

HADR can reduce outage by maintaining a log-replaying standby, but replication can also reproduce an unwanted delete or other logical change. Keep independent backup/recovery capability even when availability architecture is strong.

A role change should be a service decision based on HADR state, log gap, replay health and data-loss expectations—not a generic way to “reset” a degraded standby.

5. Maintenance changes metadata or physical organization​

RUNSTATS refreshes optimizer statistics; REORG changes physical organization; REORGCHK evaluates indicators. Their names often appear together, but their purposes differ.

Condition-driven maintenance asks:

  • what changed in the data/workload?
  • what metric or plan evidence indicates a problem?
  • which utility changes the relevant state?
  • what is its availability/log/temp/storage cost?
  • what evidence proves success afterward?

6. Monitoring and diagnostics narrow the causal domain​

Use lightweight current-state tools first where appropriate: SQL monitoring functions, administrative views, db2pd, dmctop, utility status and event monitors. Escalate to deeper diagnostic collection (db2diag, support collections, FODC/trace) when the causal domain or vendor-support requirement justifies it.

Retrieval practice Explain why a completed LOAD, a successful BACKUP and a green monitoring dashboard are each insufficient by themselves to prove that an application service is safe and recoverable.

What to carry into the practical part​

For every Part 2 utility or recovery action, record:

  1. starting state and business objective;
  2. operation/options and expected state transitions;
  3. monitoring/diagnostic evidence during execution;
  4. resulting database/table/HADR state;
  5. recovery implications;
  6. application or workload validation.
