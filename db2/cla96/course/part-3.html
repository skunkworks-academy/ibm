Part 3: security, access control & concurrency

Recommended time: 8 hours

Security and concurrency share a DBA requirement: understand who can do what, against which data, under which transaction semantics, with what evidence.

Unit 1 · Concurrency is correctness under simultaneous work​

Multiple applications can read and change the same data at the same time. Db2 protects correctness through mechanisms that include locking and versioning behavior governed by transaction isolation and access patterns.

The DBA’s job is not to “remove locks.” The job is to understand:

  • what transaction holds the resource;
  • what another transaction requests;
  • lock mode and object scope;
  • transaction duration and commit behavior;
  • isolation level;
  • access path and number of rows/pages touched;
  • whether escalation, timeout or deadlock behavior is involved.

Lock symptoms are not all the same​

Lock wait — one unit of work waits for another to release an incompatible lock.

Lock timeout — a wait exceeds the configured timeout and the waiting operation is ended.

Deadlock — two or more units of work form a dependency cycle; Db2 chooses a victim to break the cycle.

Lock escalation — many lower-level locks are replaced by a higher-level lock to control lock-list usage, potentially increasing contention.

Unit 2 · Isolation levels: visibility vs concurrency​

Db2 isolation levels commonly discussed in the CLA96G scope are:

IsolationGeneral intentTypical trade-off
UR — Uncommitted ReadMaximum read concurrency where dirty-read semantics are acceptableCan observe uncommitted data
CS — Cursor StabilityCommon transactional balance; protects the current row appropriatelyRe-reading can observe change depending on access pattern
RS — Read StabilityRows that qualify during the unit of work are protected from changeMore locks / lower concurrency than CS
RR — Repeatable ReadStrong protection across the qualifying range/setHighest concurrency cost among these levels

The correct level is an application correctness decision. A DBA should not lower isolation simply to make lock waits disappear.

Unit 3 · A lock-triage runbook​

Use a repeatable sequence:

01 · Confirm symptomWait time, timeout/deadlock messages, affected service and start time.
02 · Find blockersIdentify waiting and holding application handles plus the locked object.
03 · Capture contextSQL, transaction age, isolation, application identity and recent changes.
04 · Remediate safelyPrefer application/transaction correction; force/terminate only with understood business impact.
05 · Prevent recurrenceReview commit scope, indexing/access path, batch overlap, timeout and workload design.

A forced application can roll back work and affect user transactions. Treat it as an operational change with impact, not a diagnostic click.

Unit 4 · Authentication vs authorization​

Authentication establishes identity. Depending on platform and configuration, identity may be validated through operating-system or external mechanisms.

Authorization determines what an authenticated identity can do inside Db2.

Do not conflate these failure domains:

  • “password rejected / identity not established” is an authentication path;
  • “SQL0551N / not authorized” is an authorization path;
  • successful connection but denied object access is not a network problem.

Least privilege and separation of duties​

Avoid using broad administrative authority as a convenience mechanism. Build access from roles and task requirements.

A practical authorization review asks:

  1. Which identity or role is the subject?
  2. Which operation is required?
  3. Which database/schema/object is in scope?
  4. Which authority or privilege is the minimum sufficient grant?
  5. Who is allowed to grant it?
  6. Is the grant temporary or permanent?
  7. How will it be reviewed and revoked?

Unit 5 · Administrative authorities​

The current public CLA96G objectives explicitly call out task authorities including SECADM, DBADM, ACCESSCTRL and DATAACCESS.

SECADM​

Security administration authority is intentionally powerful and separated from ordinary database administration. Use it for security policy and authority administration tasks that should not be casually mixed with application operations.

DBADM​

Database administration authority provides broad administrative capability for a database, but does not mean “security superuser.” Current Db2 documentation defines boundaries and exceptions; validate them for your service level rather than assuming DBADM can perform every security task.

ACCESSCTRL​

Access-control authority supports managing grants/revokes without automatically granting access to all application data.

DATAACCESS​

Data-access authority provides broad access to user data. It is operationally sensitive and should not be used as a substitute for proper application roles.

Design roles around duties

Examples: APP_DEPLOYER, REPORT_READER, DBA_OPERATOR, PERF_ANALYST. Role names should describe responsibility, not a person.

Unit 6 · Roles and object privileges​

Prefer roles when several users or service identities perform the same controlled function.

Illustrative pattern:

CREATE ROLE REPORT_READER;
GRANT SELECT ON TABLE APP.SALES_SUMMARY TO ROLE REPORT_READER;
GRANT ROLE REPORT_READER TO USER ANALYST1;

The exact privilege model depends on object ownership, implicit privileges, authorities and group/role paths. During an authorization incident, inspect the effective path, not only direct grants.

Review questions for a privilege grant​

  • Can the task be done with object privilege instead of database authority?
  • Can a role replace repeated user-specific grants?
  • Does the role cross environments or tenants unexpectedly?
  • Is grant option required? Usually it should be avoided unless delegation is intentional.
  • Is there a review/expiry process?

Unit 7 · RCAC: row permissions and column masks​

Row and Column Access Control (RCAC) enables fine-grained policy enforcement inside Db2.

Row permissions can restrict which rows are visible/operable for a user or session context.

Column masks can transform or hide sensitive column values under policy.

RCAC is powerful because the policy remains close to the data, but that also means testing must include:

  • privileged and non-privileged identities;
  • application service accounts;
  • ad-hoc SQL/reporting users;
  • maintenance and ETL processes;
  • performance impact on representative queries;
  • policy change and rollback procedures.

Unit 8 · LBAC and policy choice​

Label-Based Access Control (LBAC) applies security labels and authorizations to protect data according to a label model. It can suit classification-style policies where data and users carry defined security labels.

Choose between RCAC, LBAC and ordinary privileges based on the policy model. Do not stack controls simply because they exist; every layer adds governance, testing and troubleshooting complexity.

A design comparison should consider:

RequirementLikely control family
Broad role/object accessAuthorities, roles and privileges
Filter rows by session/user/business ruleRCAC row permissions
Mask sensitive column valuesRCAC column masks
Classification/label policyLBAC
Controlled identity switching in tiered applicationsTrusted context

Unit 9 · Trusted contexts for multi-tier applications​

In a three-tier architecture, a middleware connection may need to act on behalf of end users without creating an unmanaged pool of fully privileged credentials.

A trusted context can define conditions under which trusted connections and controlled user switching are permitted.

Evaluate:

  • trusted system/network attributes;
  • service identity ownership;
  • which users may be switched to;
  • which roles become available;
  • auditing requirements;
  • failure behavior when trust conditions are not met.

Do not use a trusted context as a way to hide user attribution. Its purpose is controlled delegation, not anonymity.

Unit 10 · Encryption in transit and at rest​

Security architecture should distinguish:

  • data in transit — protect client/server connections with supported TLS configurations and certificate governance;
  • data at rest — database/storage encryption controls, key management and backup protection;
  • credentials/secrets — store outside scripts and source repositories; rotate according to policy.

A “TLS enabled” checkbox is not a complete control. Review protocol versions, certificate validity, hostname verification, trust stores, key ownership and renewal automation.

Unit 11 · Auditing and evidence​

Audit design answers which events must be attributable and reviewable. Examples include:

  • privileged security changes;
  • grant/revoke activity;
  • access to regulated tables;
  • authentication failures;
  • administrative actions;
  • policy changes.

Audit volume can be significant. Define retention, protected storage, review ownership, alerting and access controls around the audit trail itself.
