Part 1: foundations, configuration, storage & data movement

Recommended time: 9 hours

Part 1 establishes the operational model that every later recovery, security and performance decision depends on. The key skill is scope awareness: know whether a fact or change belongs to the operating system, Db2 installation, instance, database, schema or object layer before acting.

Unit 1 · Db2 12.1 architecture and service-level thinking​

A relational DBA needs a mental map of the runtime:

Operating system / host
└── Db2 installation / code level
    └── Db2 instance (database manager runtime)
        ├── database A
        │   ├── schemas
        │   ├── table spaces
        │   ├── tables / indexes / views
        │   └── logs / recovery history
        └── database B

This hierarchy is not just terminology. It tells you the likely blast radius of a failure or change.

  • A listener or instance-start issue can affect several databases.
  • A database configuration change is normally scoped to one database.
  • A table privilege issue may affect one object or role path.
  • A storage-full condition can manifest as utility, logging or availability symptoms depending on the filesystem and object involved.

Service levels: avoid saying only “we run 12.1”​

Maintenance planning requires the precise installed level. IBM’s current CLA96G objectives explicitly include the Db2 versioning/service model. Record enough detail to distinguish the base version, maintenance level and the target being considered.

Your change record should answer:

  1. What exact code level is installed?
  2. What is the target level?
  3. What prerequisites and operating-system compatibility apply?
  4. Is the change online, deferred or restart-dependent?
  5. What is the rollback or fallback position?
  6. Which databases and clients share the installation/instance?

Unit 2 · Command-line discipline and configuration control​

The command-line processor is valuable because it is scriptable, reviewable and repeatable. Enterprise administration should favor commands that can be captured in change records and runbooks over undocumented GUI-only actions.

Baseline database configuration​

A typical inspection begins with:

db2 get db cfg for SAMPLE

Do not copy the entire output into a ticket without interpretation. Identify the parameters relevant to the decision, their current values, and whether they are automatic, dynamic or restart-sensitive in your exact environment.

A controlled update pattern is:

# 1. Capture current value(s)
db2 get db cfg for SAMPLE

# 2. Apply one justified change
db2 update db cfg for SAMPLE using <PARAMETER> <VALUE>

# 3. Confirm effective configuration
db2 get db cfg for SAMPLE

# 4. Validate workload / health evidence
# 5. Record rollback value and outcome

RESET DB CFG and AUTOCONFIGURE are not shortcuts around understanding. Treat automatic recommendations as inputs to a decision, not as an authorization to change production.

Scope checklist before changing configuration​

Scope

Is this instance configuration, database configuration, registry, workload manager, operating system or application configuration?

Activation

Does the value take effect immediately, on connection, on database activation, or after an instance restart?

Evidence

Which metric, symptom or capacity model justifies the change, and what result would prove it helped?

Unit 3 · Instances, databases and operational lifecycle​

Instance lifecycle commands are simple; instance lifecycle decisions are not.

Before db2stop or db2start, consider:

  • connected applications and in-flight work;
  • HADR or other availability roles;
  • automation that may reconnect or restart services;
  • filesystem, port and operating-system dependencies;
  • current diagnostic evidence;
  • the business impact and change approval.

A restart can be a valid remediation, but it should not become the default diagnostic technique.

First-response evidence for an instance-level symptom​

1. Time and user-visible symptom
2. db2level / instance identity
3. process and instance state
4. listener/service/port reachability
5. recent OS, network or configuration changes
6. db2diag and relevant operating-system logs
7. impact across databases / clients
8. action taken and validation result

Unit 4 · Database creation, storage and table spaces​

Storage design affects performance, capacity, backup/recovery and operational risk.

When creating or expanding a database, think in terms of workload characteristics rather than only initial size:

  • expected data growth;
  • transaction log generation rate;
  • backup image size and backup window;
  • archive-log throughput;
  • temporary workload peaks;
  • LOB or large-object growth;
  • storage latency and failure domains;
  • recovery time objectives.

Separate concerns where the platform allows​

Data, active logs, archived logs and backup images have different I/O and retention patterns. Separating them can reduce contention and reduce the chance that one full filesystem disables several recovery mechanisms at once.

Capacity is a recovery control

A database with adequate data space but no room for logs or archive logs can still suffer an outage. Capacity monitoring must include recovery-related storage, not only table-space utilization.

Table-space reasoning​

Know the answers to these questions for important databases:

  • Which table spaces hold critical application data?
  • Which are automatic storage vs explicitly managed?
  • Which objects are large or fast-growing?
  • What is the high-water mark and free-space trend?
  • Which storage paths are shared with logs, backups or other databases?
  • What would happen if one path became unavailable or full?

Unit 5 · Database objects and least-surprise design​

Core objects include schemas, tables, indexes, views, sequences and temporary structures. A DBA should be able to explain both what an object does and what operational cost it introduces.

Schema strategy​

Use schemas to create understandable ownership and security boundaries. Avoid an environment where every team creates objects under arbitrary owners and privileges are granted individually without roles.

Index strategy​

Every index is a trade-off:

Potential benefits

  • fewer rows/pages examined for selective access;
  • support for ordering, joins and uniqueness;
  • reduced response time for critical read paths.

Potential costs

  • additional storage;
  • maintenance on INSERT/UPDATE/DELETE;
  • longer LOAD/maintenance operations;
  • more optimizer choices and governance overhead.

Do not create indexes because a query “looks slow.” Use workload evidence and EXPLAIN later in Part 4.

Views as an interface​

Views can simplify application access and help expose curated columns/rows, but a view is not automatically a security control. Privileges, RCAC/LBAC and ownership rules still matter.

Unit 6 · Data movement: EXPORT, IMPORT and LOAD​

The public CLA96G objectives explicitly include EXPORT, IMPORT and load operations. The important distinction is the operational behavior and recovery implication of each method.

EXPORT​

Use EXPORT to extract data to a supported external representation. Before exporting production data, classify whether the output contains regulated, personal or confidential content and protect the file accordingly.

Example learning pattern:

db2 "export to employees.del of del select empno, lastname, workdept from employee"

IMPORT​

IMPORT processes input through SQL-style operations. It is often simpler operationally but may be slower for very large bulk movement than LOAD.

db2 "import from employees.del of del insert into employee_stage"

LOAD​

LOAD is designed for high-throughput bulk ingestion and has table-state, logging and recoverability considerations that require deliberate monitoring.

Do not treat this as fire-and-forget:

db2 "load from employees.del of del insert into employee_stage"
db2 list utilities show detail

Depending on the operation and environment, inspect utility messages and table state before handing the database back to users.

Unit 7 · RUNSTATS and REORG as maintenance tools, not rituals​

You will revisit performance in Part 4, but establish the maintenance distinction now:

  • RUNSTATS refreshes statistical metadata used by the optimizer.
  • REORG physically reorganizes table or index data structures under supported options.
  • REORGCHK helps identify candidates using statistical criteria; it is not a universal command to run before every performance incident.

A maintenance calendar should be informed by change rate, workload behavior, object size and maintenance cost.

# Illustrative only — validate exact syntax/options for your environment
db2 "runstats on table APP.ORDERS with distribution and detailed indexes all"
db2 reorgchk current statistics on table APP.ORDERS
Think in evidence loops

After large data change: refresh the statistics justified by the workload → inspect relevant access plans → measure runtime behavior → decide whether physical reorganization or index changes are warranted.
